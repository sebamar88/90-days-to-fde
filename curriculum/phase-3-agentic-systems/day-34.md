# Day 34 — Validate tool inputs and outputs

## Why this matters

Tool calls and tool results are untrusted data, even when generated by the system's own model or returned by an internal service. Validation prevents malformed values from becoming actions.

## Scenario

A simulated directory service sometimes returns missing region fields, unexpected properties, or a response that does not match the requested site.

## Outcomes

- Validate at both the orchestration boundary and the integration boundary.
- Reject mismatched, incomplete, and oversized results.
- Preserve a safe error state rather than guessing missing values.

## Exercise

Write contract tests using valid output, missing region, unexpected property, wrong site ID, and wrong data type. Validate the response before it enters workflow state. Map invalid output to a stable `dependency_contract_error`; do not expose raw payloads to the coordinator. Add a fixture showing that a failed lookup cannot enable the draft action.

## Deliverable

Boundary-validation tests, a typed error mapping, and a short note describing which component owns each validation check.

## Assessment

Pass when every invalid response is rejected, the workflow remains non-writable after rejection, and diagnostics retain a correlation ID without logging raw input.

## Reflection

Why validate a response from an internal service instead of trusting the service owner?
